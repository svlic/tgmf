# 恢复正确性：分阶段修复计划

日期：2026-10-29。依据：[ADR-0008](adr/0008-job-lifecycle-recovery.md)、[技术债务](technical-debt.md) TD-02～07、TD-09／12／17。
本文件只描述计划，**没有实施下列代码改动**。范围保持自用、单服务器、单 Worker，不引入分布式队列或重做传输服务。

## 目标与非目标

已确认目标是“继续同一任务尚未完成的内容”，而不是清空进度、从头发送：

- 不重发已确认的终态内容；源 ID 不存在可跳过。
- 逐条当前结果、任务汇总和最终状态能够对上。
- 暂停／取消确认后，旧执行不能继续推进或覆盖新状态。
- full_group 不被恢复逻辑悄悄拆组。
- 不把“远端可能成功、本地未确认”伪装成已成功或可安全重试。

不承诺 Telegram 与 SQLite 之间的分布式事务或端到端 exactly-once；不在本轮优先重做历史浏览、密钥轮换、UI 风格。

## 阶段 0：确定恢复契约并建立失败样例

**做什么**

1. 明确区分任务状态、每条消息当前结果、累计发送尝试三个概念。
2. 建立状态转移表，定义 paused／failed／pending／running／completed／cancelled 的合法动作及 Worker 归属。
3. 暂时保持 sent／warn／skipped 终态，不擅自把 warn 变为可重试。
4. 在已有测试文件中，以临时 SQLite 和受控 Telegram 客户端构造失败样例，不触碰真实账号和生产库。

**必须澄清但不阻塞其他阶段的两个决定**

- 无目标 ID／发送后响应丢失：不重复优先，还是补齐优先？建议先保守标记不确定，提供明确核查路径，不自动重发。
- 搜索恢复：固定首次选集还是重新搜索？建议需要可复现任务时采用固定选集，但这是建议，不是已经批准的变更。

**通过条件**：以下每个阶段都有先失败的具体样例和独立预期；未决语义不会被默认埋进代码。相关文件为 `service.test.ts`、`repositories.test.ts` 及现有 API／表单测试边界；避免先做大规模拆文件。

## 阶段 1：让结果记录和计数在恢复后仍然一致

对应 TD-03，主要位置：[仓储](../src/lib/db/repositories.ts)、[processJob](../src/lib/telegram/service.ts)。

**建议实现方向**

- 每条当前结果以 message_transfer_records 为依据，任务结果计数作为派生汇总；发送尝试数单独累计。
- 记录状态转移与计数差额在同一本地事务完成，或选择可验证的记录重算方案；实现时比较两者成本，避免同时保留两套竞争的事实来源。
- 相册逐成员落库后遇限流／中断，不应丢失已经保存成员的汇总；failed→sent 应移除旧失败结果，而不是再叠一次 processed。
- 恢复前提供旧数据汇总校正路径；不删除终态，不清零尝试历史。先在副本检查旧计数与记录差异。

**验收**：单条失败后成功，最终只计一个结果；copy 两条中第一条成功、第二条限流后继续，最终正确计两条；记录保存后、汇总前中断可恢复；重复提交同一结果不重复累计。

**交付边界**：先兑现内部一致性，不开放新的 failed 恢复入口。旧库兼容与差异校正需随改动验证。

## 阶段 2：把“请求停止”和“已经停止”分开

对应 TD-05，主要位置：[任务 API](../src/app/api/jobs)、[Worker](../worker/index.ts)、仓储和 processJob。

- 生命周期动作使用带原状态条件的 UPDATE，只修改必要字段，禁止整行旧计数回写。
- 保留明确的执行归属，停止尚未确认前不能开始另一轮同任务执行；是否需要持久化请求字段由最小实现决定。
- 在搜索分页、相册成员和可中断长操作的安全点检查控制请求。已经进入远端 RPC 的发送不能承诺立即撤回，界面应显示“停止请求已接受”，而不是提前保证已停。
- 完成、限流退回和异常退出仅允许当前有效执行更新状态；SIGTERM 建立有界退出策略，不只写 stale 后继续发。

**验收**：Worker 完成与 Pause 竞争不复活 completed；暂停立即恢复不启动两轮；copy 中取消不继续后续成员；SIGTERM 后恢复保留已确认结果；所有控制动作不覆盖新计数。

**交付边界**：先修控制协议，再接对用户可用的继续入口。不要为单 Worker 引入分布式锁。

## 阶段 3：处理相册和不确定发送，防止恢复盲目重发

对应 TD-04／07／08，主要位置：相册补取、forward 映射与发送记账。

- 检查整个相册已有结果，不能只看主循环当前 ID。
- 全部终态：不再发送；全部确定未发送：可按原组处理；部分确认／部分不确定：进入明确恢复分支，不直接整组重发，也不静默拆组。
- 推荐先保守隔离不确定组并显示原因；若用户要求自动补齐，再调查 Telegram 请求幂等标识跨重启保存与对账，不能凭本地事务声称解决。
- 注入发送成功但响应丢失、返回后写库失败、上传成功但文件清理失败，分开发送结果与附带清理错误。

**验收**：相册只有一成员已确认时，恢复不重复发送它、不覆盖其终态，也不把残组伪装成 full_group 完成；不确定组可见且有处理路径；正常整组与 captioned_only／非相册控制用例保持行为。

**交付边界**：未明确部分组／不确定结果取舍前，不以“自动恢复已完善”交付。copy 真正整组上传是另一项能力，不顺带混进此次恢复修复。

## 阶段 4：安全开放 failed 的“继续未完成”

对应 TD-02，依赖阶段 1～3；主要位置：[resume API](../src/app/api/jobs/[jobId]/resume/route.ts)、[动作按钮](../src/components/dashboard/forms.tsx)。

- 为可恢复 failed 任务提供明确 Continue 操作，复用 job ID、配置及确认结果；不要恢复已取消／已完成任务，不删除失败记录来绕过计数。
- 恢复只排队，不在 API 请求里执行传输；错误原因仍可追踪，不确定项目保持可见。
- 将用户看到的状态与动作响应对齐，补 mutation 在途请求后的必要刷新，避免后端已排队、界面仍停 paused／failed。

**验收**：UI 创建→启动→注入部分失败→排除原因→继续同一任务→完成；确认内容只发送一次，失败内容按策略重试，统计与记录一致；重复点击或旧页面发动作返回明确冲突而不重复排队。

**交付边界**：这是首个对用户开放的恢复能力里程碑，不是第一步改按钮。

## 阶段 5：覆盖自动恢复、长搜索与实际部署中断

对应 TD-06／09／12，以及前述恢复链。

- 选择并落实搜索选集契约；分阶段维护心跳和暂停／取消检查，不静默截断命中。
- 核对 SDK invoke 的短 Flood Wait，将等待责任收敛到应用调度，验证 A 冷却时唯一 Worker 能处理 B。
- 在临时数据库和模拟远端上模拟进程退出／重启，随后在经授权的测试 Telegram 账号与隔离目标频道验证关键场景。
- 旧数据升级前停 Web／Worker 并备份配套数据／密钥；只在副本演练修正与恢复。不得为了测试恢复而启动指向生产源／目标的副本 Worker。

**验收**：自动冷却恢复、进程重启、两账号切换、搜索编辑／新增／删除、正反序相册、升旧库均符合已确定契约；lint、typecheck、完整测试与 build 通过，补充真实栈验证证据。代码／结构检查不替代远端行为核查。

## 推荐提交和交付顺序

阶段 0 的契约与回归样例 → 结果／计数一致性 → 停止和归属协议 → 相册／不确定结果 → failed 入口及界面同步 → 搜索／SDK 与重启验证。

每个阶段可以用小提交评审，但只有依赖闭合后才称“恢复正确性已交付”。预计改动集中在现有仓储、service、Worker、任务 API 和动作组件；是否添加 schema 字段取决于阶段 0／2 的设计，不提前承诺无需迁移。
本计划不包含多 Worker、跨机锁、数据库替换、全站 UI 重写，也不安排自动生产部署。远端不可确认的发送结果始终是明确保留的可靠性边界。
