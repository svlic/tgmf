# ADR-0014：自动生成持久密钥，保留环境覆盖

- 状态：已采用；密钥生命周期问题由用户明确留待后续。
- 历史时间：2026-10-23；重建时间：2026-10-29。
- 原候选：17。

## 前后方案与证据（A）

原来 APP_ENCRYPTION_KEY 必填。[f02f913](https://github.com/svlic/tgmf/commit/f02f913) 改为未设置或空字符串时，在数据库目录生成 app-encryption.key；内存数据库则使用 data 目录。
非空配置优先且仍要求至少 32 字符；错误配置不静默换成新密钥。
先创建随机临时文件（0600），再通过硬链接发布完整文件；竞争者读取已发布密钥，不覆盖胜者。损坏文件报错，不自动重生成。
当前：[密钥加载](../../src/lib/env.ts)、[AES-GCM 加密](../../src/lib/crypto.ts)、[备份约束](../../README.md)。

## 原因与分析

- **A**：提交正文明确自动持久化、并发 Web／Worker 共享、保留覆盖值。
- **B**：减少首次部署手工配置，但不消除运维保管责任。
- **U**：后续密钥管理问题待以后解决；不是本次已完成轮换或恢复设计。

## 不可忽略的后果

旧环境密钥不会自动迁移到文件；删除旧值将使旧密文无法解密。数据库和密钥应一起备份恢复，使用环境覆盖时需另行安全备份原值。
只泄漏数据库与同时泄漏数据库和密钥，是不同威胁；同目录存放不抵抗整目录泄漏。依赖本地文件系统的权限及硬链接语义。
尚未提供轮换／重新加密、密钥丢失恢复保证。将其登记为延期事项，而不是为个人部署立即引入 KMS。见 TD-20。
