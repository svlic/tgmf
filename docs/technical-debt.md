## 评估前提

这是潜在债务登记，不是线上事故报告，也不是本次已修复列表。只新增文档，不修改应用、部署或数据库。
按用户已确认的目标评估：**自用、单服务器、单 Worker；账号冷却不要阻塞其他账号；恢复继续未完成；full_group 尽量保留相册；大文件使用文件优化；历史记录几乎不看；认证交给 Web 服务器；密钥生命周期后续解决；CI 为节省服务器资源。**

- **A（事实）**：能从代码／配置直接确认；不等于运行时已经发生故障。
- **B（分析）**：由代码路径推演的触发条件和后果，尚未在实际栈复现。
- **C（未知）**：业务取舍、部署状态或规模数据待确认。
- **V（隔离验证）**：仅对标注的小范围 SQL／算术做实验，不扩大为端到端验证。
- **P1**：优先封住安全边界或核心恢复缺口；**P2**：近期正确性、可控性和可靠性；**P3**：按实际规模加固／优化；**待决／延期**：先定契约，不擅自实现。

建议顺序：先核实 TD-01 的部署入口；再把 TD-02～05、07 作为恢复正确性的一组工作；TD-09／10 兑现账号不阻塞和节流；之后处理监控、迁移和发布门禁。不要直接把所有条目变成大重构项目。

## 核心安全与恢复

### TD-01：应用端口可能绕过外层认证

- **A／证据**：[Compose](../docker-compose.yml) 使用 `54001:3000`，没有绑定 loopback；[CSRF](../src/lib/csrf.ts) 仅做来源检查。应用已删除内置认证，见 ADR-0013。
- **B／触发**：如果不可信网络能直连 54001，代理登录就不是必经入口。没有探测当前宿主防火墙／公网，不认定线上已暴露。
- **最小建议**：同宿主代理绑定 loopback；容器代理使用私有网络，避免直接发布应用端口。外层保护覆盖页面和全部 API，不重建应用密码系统。
- **验收**：从非可信网络直连失败；代理入口未认证时 UI、GET 与 mutation API 均被拒绝；认证后请求正常。此验收需要部署权限，本次未执行。

### TD-02：failed 任务缺少“继续未完成”入口

- **A／证据**：[resume API](../src/app/api/jobs/[jobId]/resume/route.ts) 只接受 paused；[按钮](../src/components/dashboard/forms.tsx) 同样只在 paused 开启 Resume；[Worker](../worker/index.ts) 异常会产生 failed。
- **影响**：符合“记录非终态可重试”的执行器，不等于用户能继续 failed 任务。搜索／网络异常后，用户无法经现有入口继续原任务。
- **最小建议**：定义 failed→pending 的条件和明确 Continue 操作，保留 sent／warn／skipped，不简单新建或清空任务；必须联动 TD-03／04／07，不能只把 API 状态限制删掉。
- **验收**：中途失败后排除原因，通过 UI 继续同一 job；此前确认终态不重发，剩余内容处理完后状态、记录和计数一致。

### TD-03：记录重试成功，不会自动消除旧失败累计

- **A／证据**：[仓储 recordProgress／upsert](../src/lib/db/repositories.ts) 分别增量累计任务计数和覆盖单条记录；[processJob](../src/lib/telegram/service.ts) 最后按累计 failed_messages 判断 failed，没有成功转移时扣除旧失败。
- **B／例子**：某条先 failed，恢复时变 sent，记录已成功，但旧 failed_messages 仍可保留；processed 也可能重复累计。copy 相册在前几个成员已保存后遇 Flood Wait，批量进度尚未提交就返回，恢复跳过终态又可能漏计先前成功成员。
- **最小建议**：先定义“当前每条结果”与“累计尝试次数”两个口径；记录状态转移和对应计数在本地事务内协调，或按记录重建结果计数；不靠恢复时把所有计数归零掩盖问题。
- **验收**：失败→成功、相册部分成功→限流→恢复、写完记录未写计数就崩溃三组场景，最终每个源 ID 的结果只计一次，尝试指标独立保留。
- **验证边界**：当前仅静态推演，未运行 processJob；不把算术直觉冒充已复现整个恢复流程。

### TD-04：发送成功与本地保存之间存在不确定窗口

- **A／证据**：[processJob](../src/lib/telegram/service.ts) 先等待 Telegram 返回，再逐条 upsert 及更新进度；没有跨重启持久化的发送请求幂等标识或已完成对账流程。数据库唯一索引只约束本地 job＋源 ID，不约束远端发送。
- **B／触发**：Telegram 已接收，但响应丢失、进程退出或写库失败。本地仍是未完成，重启再次发送可能重复。不要因 SDK 在单次调用内可能重试就推定跨进程幂等。
- **C**：用户接受源 ID 没消息，不等于接受未映射发送结果漏发／重发。
- **最小建议**：先明确不确定结果策略及人工对账；在发送边界记录尝试和不确定结果。若需要强幂等，再调查 Telegram randomId／请求标识的可持久化契约，不能靠 SQLite 事务承诺 exactly-once。
- **验收**：分别注入“远端已接收、响应未返回”和“返回后写库失败”，恢复遵守选定策略、明确显示不确定，不自动冒充成功。

### TD-05：控制状态不等于 Worker 已停止

- **A／证据**：[Pause／Resume／Cancel 仓储](../src/lib/db/repositories.ts) 经通用 setStatus 读整行再回写，UPDATE 只按 id；[API](../src/app/api/jobs/[jobId]/pause/route.ts) 的状态检查发生在写入前。Start 已有条件 UPDATE，可作为局部改法参考。[Worker](../worker/index.ts) 收到退出信号只设置 stopped 并写 stale，不打断当前 processJob。
- **B／竞争**：Web 检查 running 后 Worker 完成，Web 仍可能把 completed 写成 paused；整行回写可能覆盖新计数。paused 可能先显示，实际 RPC／copy 相册循环尚未停止；快速 Resume 又使仍运行的旧调用失去归属或错过暂停。SIGTERM 后当前任务仍可能发送直到进程被强杀。
- **最小建议**：状态动作只更新必要字段并带旧状态条件；区分“请求暂停／取消”与“已停止”，长操作／相册成员间设置安全检查点；退出时等待或中止当前操作，明确未完成处理。
- **验收**：完成与暂停交错、暂停立即恢复、copy 相册发送中取消、SIGTERM 中断四种时序均不复活终态、不覆写新计数；显示与停止确认相符。

## 选集、相册和账号节流

### TD-06：搜索选集固定还是动态，尚未决定

- **A／证据**：[搜索收集](../src/lib/telegram/search-message-ids.ts)、[processJob 搜索分支](../src/lib/telegram/service.ts) 每次重搜，仅持久化查询与计划摘要。
- **B／例子**：暂停时命中的消息被编辑，恢复后可能不再命中；新消息可能加入，总数变化。相册展开还可能处理非直接命中的成员，影响 total 口径。
- **最小建议**：二选一：接受动态搜索并明确恢复含义；或首次完整搜完后持久化 ID，恢复固定选集。用户尚未回答，不擅自批准任一方案。
- **验收**：暂停后新增／编辑／删除源消息，恢复的成员和 total 期望由 ADR 唯一确定；相册展开后的统计口径明确。

### TD-07：部分相册恢复时，forward 仍可能带上已终态成员

- **A／证据**：[processJob](../src/lib/telegram/service.ts) 主循环只检查当前 ID 的终态；copy 有 filterCopyMessagesPendingTransfer，而 forward 会对当前选出的整组调用 forwardMessages，没有同样的逐成员终态筛选。
- **B／触发**：一次相册部分确认或部分落库后中断；恢复遍历到非终态成员，又取出整组，可能带着已 sent／warn 的成员重发。简单过滤已发送成员又可能破坏完整相册，不能只复制 copy 的过滤函数了事。
- **最小建议**：把相册级发送尝试／恢复策略与 TD-04 一起定义；明确保完整相册与不重复发送冲突时的优先级，必要时将不确定组交人工处理。
- **验收**：两成员相册一条已确认、另一条未完成，恢复不盲目重发确认成员，也不把拆组恢复偷偷当成 full_group 成功；检查记录不覆盖已有终态。

### TD-08：相册发现和 copy 相册能力仍有限制

- **A／证据**：[fetchAlbumMessages](../src/lib/telegram/service.ts) 在源 ID 附近约 ±10 的窗口补取、limit 25，再按 groupedId 筛选；没有完整性确认／继续扩展。README 已披露 copy 不还原目标相册。
- **B**：full_group 只能对“已发现成员”整组判断；如果窗口未包含所有成员，可能无法兑现完整性。尚无真实 Telegram 反例，不能直接断言窗口一定漏组。
- **最小建议**：验证当前 GramJS／Telegram 相册成员相邻性和最大跨度；如果不能证明窗口足够，扩展收集或保守标记不完整。copy 整组上传是否必要，按用户完整性目标明确优先级，不混同选择和发送。
- **验收**：双方向、范围边界、搜索仅命中一成员、缺失／删除成员、窗口边缘真实响应夹具；明确完整、跳过或不确定，而不是默认为完整。copy 不承诺尚未实现的整组形式。

### TD-09：SDK 内部仍会原地等待短 Flood Wait

- **A／证据**：[应用客户端](../src/lib/telegram/client.ts) 只显式设置 connectionRetries，未覆盖 floodSleepThreshold。当前安装的 GramJS `client/telegramBaseClient.js` 默认阈值为 60 秒，`client/users.js` 的 invoke 在 FloodWaitError.seconds≤阈值时 sleep 后重试，不把错误立即交给应用。对应安装版本应以 package-lock 为准，升级时重查。
- **B／影响**：应用数据库冷却逻辑可能根本看不到短等待，唯一 Worker 仍被该账号占用，限流事件／自适应也可能漏记；这与“账号冷却不要阻塞其他账号”存在缺口。
- **最小建议**：明确由哪一层管理等待；若应用负责，配置 SDK 将等待抛出并经数据库调度，而不是叠加两套等待。排查内部重试与指标的一次尝试定义。
- **验收**：对阈值两侧模拟 SDK 行为，A 账号限流后 B 可领取任务，应用记录一次冷却事件；需经过 SDK invoke 层，不能只 mock 成直接抛错。
- **验证边界**：已读安装依赖源码，未调用真实 Telegram，不报告线上阻塞次数。

### TD-10：零基础间隔使自适应不增长，或不衰减

- **A／证据**：[输入允许 delaySeconds=0](../src/lib/validation/forms.ts)；[仓储](../src/lib/db/repositories.ts) 的 flood 公式为 min(max(adaptive, configured)×2, 300000)，成功时减 configured、最低 configured。
- **V／算术**：configured=0、adaptive=0 时 flood 后仍是 0；已有 adaptive>0 而 configured=0 时，成功也不会降低它。正的基础间隔作对照则能增长／衰减。
- **影响**：固定与自适应虽可并存，零值边界却不能达到通常预期的自适应起步与恢复。configured 大于 300 秒时，上限只约束 adaptive，实际 max 仍可能更大；不要把 300 秒描述为所有请求硬上限。
- **最小建议**：明确 0 表示完全关闭还是仅关闭固定节流；若自适应仍开启，给增长基数和恢复步长合理非零定义。
- **验收**：0／正基础、0／正自适应的组合和上限两侧均有独立期望；真正调用仓储复验，不以本次算术实验替代。

## 容量、过滤与长操作

### TD-11：批量预取没有限制整个任务的内存

- **A／证据**：[buildMessageSequence／processJob](../src/lib/telegram/service.ts) 生成整个范围数组；messageCache／groupedMessagesCache 不淘汰已处理成员；搜索先保留全量返回再提 ID。
- **B**：任务越长，缓存和 ID 集越大；50 是单次预取窗口，不是内存上限。未测实际规模，不认定已经 OOM。
- **最小建议**：先量测典型／最大任务的内存峰值，再用范围迭代器与滑动缓存减少保留对象；保留相册恢复所需的最小状态。
- **验收**：长范围、稀疏范围、无界搜索与大量相册的内存随窗口而非整个任务对象数增长；RPC 数量没有明显倒退，不遗漏边界成员。

### TD-12：搜索收集阶段不响应暂停／取消，也没有周期心跳

- **A／证据**：[processJob](../src/lib/telegram/service.ts) 在设置计划和主循环前 await 完整搜索；onHeartbeat 与控制状态检查在随后循环。[Worker](../worker/index.ts) 之前只写 claimed；stale 阈值为 [60 秒](../src/lib/constants.ts)。
- **B**：大量命中／慢网络时页面可能显示 0 total 和 stale；暂停／取消无法在搜索分页间生效。不是“没有分页只取一条”：已阅读当前 SDK getMessages／RequestIter，其未设 limit 路径可全量收集。
- **最小建议**：逐页／迭代收集，页间心跳和控制检查，显示 searching 阶段；不要为了省内存静默截断命中。
- **验收**：延迟多页搜索期间健康状态有效，暂停／取消在明确时间内生效，超过单页的命中不丢失。与 TD-06 的是否固定选集分开验证。

### TD-13：正则安全和截断不是完整的规则执行保证

- **A／证据**：[过滤器](../src/lib/telegram/message-text-filter.ts) 用 JavaScript 同步 RegExp、嵌套量词启发式检查及 4096 字符截断；[校验](../src/lib/validation/forms.ts) 接受符合该检查的规则，运行时编译失败则忽略。
- **B**：不能保证所有高回溯模式被拒绝；full_group 合并 caption 后超过截断点的黑名单正则可能不匹配，关键词却检查全文，用户不易预期。没有执行恶意正则或证明可利用 DoS。
- **最小建议**：公开并确定匹配范围；若要求完整黑名单，不默默用前缀替代全文。按实际规则需求选择限制语法／安全引擎／可终止隔离，避免直接上复杂通用执行服务。
- **验收**：4096 两侧的黑白名单、长相册文本、非法旧配置、受控高复杂度规则；运行耗时有明确预算，超限有可解释结果。

## 数据库与运维

### TD-14：迁移检查与 ALTER 跨进程竞争，失败句柄可能被缓存

- **A／证据**：[getDb／ensureColumn](../src/lib/db/client.ts) 检查列后 ALTER；整个 schema／迁移未在共同写事务中串行。database 在迁移前赋值，失败后同进程再次调用可能直接返回已赋值句柄。
- **B／触发**：旧库缺列，Web／Worker 同时首次访问，两个进程都检查到缺列，后者可能 ALTER 重复字段。新库正常启动不能反证旧库升级安全。
- **最小建议**：取得适当写锁后进行检查和迁移；全部成功后才发布缓存连接，失败关闭。先做小范围串行迁移，不因没有版本账本立即替换整套存储层。
- **验收**：临时旧库双进程并发打开、迁移途中失败再试、重复运行，均不丢数据、不半初始化；关键旧状态迁移有夹具。尚未复现竞态。

### TD-15：升级回退与备份恢复需要可执行的演练

- **A／证据**：[README](../README.md) 已要求数据库／密钥配套备份、需要一致备份时停两服务，并提醒旧镜像未必兼容新库；当前没有迁移版本账本／自动 down migration。
- **C**：未检查实际备份、保留周期或恢复结果；不能称“项目没有备份”，也不能称“有说明就能恢复”。
- **最小建议**：补停机备份／隔离恢复 runbook，记录镜像 SHA、数据目录和密钥来源。WAL 模式不要只在运行中随手复制一个 .db；环境覆盖密钥单独安全保管。恢复验证不得启动会真实发送的 Worker。
- **验收**：隔离副本 integrity_check 正常，旧密文可解密、任务／记录数量符合快照；升级失败可按配套镜像和数据恢复。人工操作仍可满足单机需求，无需立即引入自动化备份平台。

## 实时看板与交付

### TD-16：“最新 100 条”其实先取最大源 ID

- **A／证据**：[listLatestForJob](../src/lib/db/repositories.ts) 先按 source_message_id DESC LIMIT；[快照](../src/lib/jobs-dashboard.ts) 之后才按 processed_at 合并事件排序。
- **V／例子**：隔离 SQLite 使用原查询，按处理顺序插入 ID 150→1，查询仍返回 51～150，不包含最后处理的 1；后续排序无法找回未选中的记录。
- **影响**：旧记录不常看也不能忽略，因为降序任务的实时详情会漏最近活动；较小 ID 的重试同样受影响。
- **最小建议**：按处理时间先选候选集，加稳定次排序键，再与事件合并；不用因此新增历史分页。
- **验收**：降序处理 150 条、更新较小 ID、相同时间戳、与 flood 事件混排，均展示定义明确的最近 100 项。

### TD-17：操作通知被在途快照请求吞掉

- **A／证据**：[usePollJson](../src/hooks/use-poll-json.ts) 有请求时直接复用；hidden 时直接返回；没有 pending refresh 标志。[动作按钮](../src/components/dashboard/forms.tsx) 成功后只通知刷新，不应用响应里的新状态。
- **B／时序**：GET 已读到 paused 但未返回→Resume 成功→通知复用旧 GET→返回 paused→needs_polling=false，再无定时刷新。切后台时操作完成也可能丢通知。
- **最小建议**：保留去重，但 mutation 发生时确保请求完成后补刷；变为可见时校正一次，必要时采用动作响应。不要通过取消所有去重增加并发请求。
- **验收**：可控延迟复现上述时序，最终显示 pending／running；后台恢复也更新；失败请求不会永久占住 in-flight。
- **验证边界**：这是静态时序推演，本次没有浏览器复现。

### TD-18：空闲看板可能永久保留旧健康状态

- **A／证据**：[快照](../src/lib/jobs-dashboard.ts) 仅 pending／running 触发轮询，worker stale 同时在该快照计算；[事件](../src/lib/client-events.ts) 只在当前 window 派发，hook 没有 focus／visibility 校正。
- **B／场景**：无活动任务时 Worker 停止，原页面可能一直显示旧健康状态；同一用户另一标签页启动任务，原页面不收到事件也不会轮询。
- **最小建议**：空闲保留低频健康检查或页面可见时刷新，活动时继续高频；不必引入 WebSocket 或跨机器事件系统。
- **验收**：空闲期间 Worker 退出、另一窗口启动任务、标签隐藏再恢复，均在明确的时间预算内收敛。跨窗口即时一致性是否必要另定。

### TD-19：发布镜像前没有完整检查门禁

- **A／证据**：[工作流](../.github/workflows/docker-publish.yml) 直接构建并发布；[Dockerfile](../Dockerfile) 只显式运行 build，未独立执行已有 lint／typecheck／test 脚本。分支保护及远端执行结果未知。
- **最小建议**：CI 中运行既有检查，发布依赖其成功；PR 同样检查。保持服务器只拉镜像，不把测试工作放回服务器。
- **验收**：失败单测／类型错误的测试提交不能进入发布 job；正常 main 才发布双架构镜像。不要为验证门禁真的向 main 推故障提交，可在隔离分支／测试工作流验证。

## 延期和按规模加固

### TD-20：密钥生命周期明确延期

- **A／证据**：[env](../src/lib/env.ts) 支持固定环境密钥优先和自动文件，没有轮换／批量重新加密／丢失恢复工具；[README](../README.md) 已说明更换／丢失后不能解密。
- **U**：用户明确这是后续问题，不把未提供轮换冒充当前已解决。
- **最小建议**：短期保持密钥稳定并配套备份；需要轮换时先设计旧新密钥过渡、迁移事务、失败恢复，不直接替换文件。没有理由为当前自用部署立刻上 KMS。
- **验收（将来）**：旧密文迁移、并发访问、迁移中断恢复可验证；已有环境覆盖值不会静默被文件替代。密钥丢失不得承诺可恢复。

### TD-21：临时文件优化尚缺磁盘／退出预算

- **A／证据**：[copyMessage](../src/lib/telegram/service.ts) 使用系统临时目录并在 finally 删除；下载／上传进度才触发部分心跳，清理错误会从 finally 抛出，进程强杀不执行 finally。
- **B**：大文件可耗尽磁盘；无进度或节流长等待可让心跳 stale，暂停需等待检查点；发送已经成功但清理失败可能被记录为发送失败，形成 TD-04 的重复风险。没有发现实际残留文件或磁盘事故。
- **最小建议**：明确最大支持媒体／可用空间和退出策略；清理失败与发送结果分开；仅清理本应用确认不再使用的残留目录，不能无条件清空 /tmp。
- **验收**：磁盘不足、上传成功但 rm 失败、长时间无进度、SIGTERM／强杀恢复；记录不把清理问题等同未发送，空间可回收且不删其他进程文件。

### TD-22：长期数据与查询成本需要小规模预算

- **A／证据**：[overview](../src/lib/jobs-dashboard.ts) 每次载入并返回全部 jobs；详情多次读取 job／COUNT／records，未统一读事务；[schema](../src/lib/db/schema.ts) 未配置历史保留，登录临时记录按访问过期清理。
- **B**：100 条限制的是响应行数，不保证 COUNT、全量历史列表成本恒定；数据库和事件持续增长；各读取瞬间可能不同，短时数字不一致。未测实际规模，不声称已有性能故障。
- **最小建议**：按一年实际任务／记录量做测量；默认历史按需读取，必要时降低精确 COUNT 频率；有明确一致性要求才加短读事务。先确定保留政策，再提供可审查清理，不删除现有数据。
- **验收**：预期长期数据量下，响应大小、查询延迟、磁盘占用和允许的暂态差异有预算；删除政策不破坏恢复与对账。

### TD-23：运行镜像和构建输入可进一步加固

- **A／证据**：[Dockerfile](../Dockerfile) 未指定非 root 用户，复制完整 node_modules／src；运行 Worker 需要的 tsx 当前在 devDependencies。[dockerignore](../.dockerignore) 枚举部分 env 文件名，未排除所有 `.env*`；Actions 用 major tag，基础镜像是浮动标签。
- **B**：未来出现未覆盖 env 文件可进入构建上下文；运行权限及依赖面可扩大漏洞影响。没有读取真实配置、扫描线上镜像或确认凭据泄漏／可利用漏洞。
- **最小建议**：明确排除 env 通配文件并按需保留模板；安排非 root 的持久目录权限；裁剪依赖前先保证 tsx 可用；固定关键 Actions 引用并安排更新，而不是永远不升级。与 TD-19 配套。
- **验收**：使用虚构敏感文件检查上下文与镜像；非 root Web／Worker 可读写旧目录并创建 0600 密钥；依赖裁剪后两个入口正常，双架构构建可运行。具体远端验证另需授权。

## 不列为债务的已接受取舍

- SQLite、单机、单 Worker、无账号自动轮换：符合实际用途，不建议“为了架构完整”换 PostgreSQL／Redis／队列。
- 不在应用内维护管理员密码：已移交 Web 服务器；债务是入口不可绕过，而非必须重新实现登录。
- 50 条预取经验值：无需立即参数化；需警惕的是误称其为内存上限或性能最优值。
- full_group 因过滤／边界整组跳过：有当前业务／文档依据，不擅自改成部分发送。
- 源 ID 不存在记 skipped：用户已接受，不要求每个 ID 都有消息；不能延伸为接受远端发送结果不确定。
- 历史仅显示有限记录：符合“几乎不看”，不优先建设完整日志检索；TD-16 仍应修，因为它影响最近活动。
- 不接 LLM、不做多 Worker 全局 limiter、不新增测试策略 ADR、不重做视觉规范：不属于当前需求。
